# ALOOKHOR — مسیر بازیابی انتشار و اتصال وردپرس (۲۴ سپتامبر ۲۰۲۶)

## وضعیت تأییدشده

- API عمومی خود `https://alookhor.ir/wp-json/alookhor-cc/v1/topbar` نسخهٔ فعال **3.10.390** را گزارش می‌کند.
- سورس `main` این مخزن نسخهٔ **3.10.387** است. نسخهٔ فعال 3.10.390 و بسته/سورس کامل آن در `main` یا تگ‌های این مخزن یافت نشد. **از سورس مخزن روی سایت نصب نکنید** تا سورس 3.10.390 بازیابی و بررسی شود.
- `https://updates.alookhor.ir/manifest.json` و ZIP نسخهٔ 3.10.387 از بیرون **HTTP 404** دارند. آخرین مانیفست ثبت‌شده در `main/public/manifest.json` نسخهٔ 3.10.385 است.
- اسکرین‌شات‌های تست cURL از `venusonlineshop.ir` به‌تنهایی اتصال خروجی سرور `alookhor.ir` را مشخص نمی‌کنند.
- اجرای [تشخیصی GitHub Actions با Secretهای جدید](https://github.com/emeliijaddd-png/alookhor-update-publisher/actions/runs/35978744481) از بیرون: سایت 3.10.390، کانال آپدیت HTTP 404، آینهٔ گیت‌هاب 3.10.385. درخواست‌های `GET /wp-json/wp/v2/users/me` و `/wp-json/alookhor-cc/v1/status` هر دو HTTP **401** گرفتند؛ کد امنِ گزارش‌شده از خود وردپرس **`invalid_username`** بود. این نشان می‌دهد نام کاربری ثبت‌شده در `WP_USERNAME` با login واقعی کاربر تطابق ندارد (یا با قالب نادرست ذخیره شده است)، نه اینکه تا این مرحله بتوان بسته‌بودن ۴۴۳ را نتیجه گرفت. مقدار را حدس نزنید و رمز را در چت نفرستید.

## کاری که در این شاخه انجام شده

- push معمولی `main` دیگر مجوز **deploy** ندارد؛ برای انتشار، تگ نسخه و گذر از تست‌های بسته/نسخهٔ سایت لازم است.
- ساخت بسته‌ای با PHPهای جایگزین‌شده با stub یا فایل CSS/JS فراخوانی‌شده ولی مفقود، رد می‌شود؛ سورس فعلی 3.10.387 به همین علت عمداً رد می‌شود.
- قبل از تغییر مانیفست عمومی، ZIP آپلودشده با HTTPS و SHA-256 از بیرون خوانده و بررسی می‌شود؛ بعد از تغییر اتمی مانیفست نیز پاسخ HTTPS تأیید می‌شود. موفقیت FTPS به‌تنهایی کافی نیست.
- اجرای تشخیصی workflow فقط **خواندنی** است: درخواست‌های عمومی به سایت/کانال/آینهٔ گیت‌هاب و در صورت تنظیم دسترسی، فقط دو GET به `/wp-json/wp/v2/users/me` (بررسی اعتبار/مجوز) و `/wp-json/alookhor-cc/v1/status`. هیچ endpoint نصب، تغییر تنظیمات یا ثبت سفارش صدا زده نمی‌شود. خروجی هرگز متن کامل پاسخ خصوصی یا رمز را ثبت نمی‌کند.
- این تغییرات تا زمان ادغام‌شدن PR روی `main` فعال نمی‌شوند؛ **PR را پیش از تأیید شرایط استقرار/دسترسی بررسی کنید.** هیچ انتشار تولیدی با این شاخه انجام نشده است.

## حداقل دسترسی لازم برای تشخیص از خود وردپرس

1. در وردپرس، `کاربران → افزودن` یک کاربر جدا برای بررسی بسازید. **اگر** نقش `ALOOKHOR Publisher` قبلاً روی سایت فعال است، همان نقش با مجوز `update_plugins` کافی است؛ در غیر این صورت، برای شروع فقط با هماهنگی مالک یک کاربر مدیریتی **موقت** ایجاد و پس از کار لغو کنید. لازم نیست رمز ورود اصلی مدیر را به کسی بدهید.
2. در `کاربران → شناسنامهٔ همان کاربر → رمزهای کاربردی (Application Passwords)` رمز جدیدی با نام مشخص مثل `ALOOKHOR GitHub Diagnostics` بسازید.
3. در وردپرس `کاربران → همهٔ کاربران`، مقدار دقیق ستون **نام کاربری / Username** حسابی را که رمز کاربردی جدید برایش ساخته‌اید بخوانید؛ این مقدار «نام نمایشی»، «نقش»، یا رشته‌ای شامل `WP_USERNAME=` نیست. در GitHub `Settings → Environments → production-diagnostics → Environment secrets` فقط Secret `WP_USERNAME` را با همان login دقیق **Edit** کنید؛ اگر `WP_APP_PASSWORD` برای کاربر دیگری ساخته شده، آن را نیز با رمز کاربردی همان کاربر هماهنگ کنید. هیچ‌کدام را در چت یا تصویر نفرستید. طبق API گیت‌هاب این محیط هنوز Required reviewer ندارد؛ لطفاً در همان صفحه خودتان را به‌عنوان **Required reviewer** انتخاب و `Save protection rules` را بزنید، سپس Secretها را نگه دارید.
4. پس از تصحیح نام کاربری فقط بگویید «اصلاح شد»؛ عامل یک بار دیگر روی شاخهٔ جداگانه تشخیص فقط‌خواندنی را اجرا و سپس تریگر موقت را حذف می‌کند. اجرای دستی Actions از اتصال فعلی Arena با HTTP 403 رد شد؛ برای اجرای دستی در آینده می‌توان اتصال GitHub را با Actions: write بازمتصل کرد، ولی **برای این مرحله لازم نیست**. پس از پایان پروژه رمز کاربردی و دسترسی اضافی را لغو کنید.

## برای تشخیص واقعی محدودیت ۴۴۳ از **سرور خود آلوخور**

- پاسخ endpoint مدیریتی، درخواست سرور وردپرس به **آدرس مانیفست تنظیم‌شده** و خطای آن را نشان می‌دهد؛ درخواست‌های عمومی workflow از GitHub Runner اجرا می‌شوند و نشان‌دهندهٔ خروجی وردپرس نیستند.
- اگر باید هر دو `raw.githubusercontent.com` و `cdn.jsdelivr.net` مستقلاً از روی **هاست alookhor.ir** تست شوند، به دسترسی WP-CLI/SSH محدود روی همان هاست یا کمک پشتیبانی میزبانی نیاز است. از پشتیبانی بخواهید با WordPress HTTP API (`wp_safe_remote_get`)، TLS certificate verification روشن و timeout کوتاه، به URL عمومی کوچک روی هر دو دامنه و به `updates.alookhor.ir/manifest.json` درخواست GET بزند و فقط HTTP status یا کد خطای cURL را گزارش کند. تست روی `venusonlineshop.ir` معتبر نیست.
- اگر واقعاً ۴۴۳ برای آن دامنه‌ها از همان هاست بسته باشد، تغییر فایروال/allowlist فقط از پنل یا پشتیبانی هاست انجام می‌شود؛ رمز وردپرس یا GitHub آن را باز نمی‌کند. غیرفعال‌کردن بررسی TLS یا استفاده از پراکسی عمومی/سایت ثالث راه‌حل ایمن نیست.

**متن آمادهٔ درخواست از پشتیبانی هاست:** «لطفاً از خود سرور میزبان `alookhor.ir` (نه یک وب‌سایت دیگر) با WordPress HTTP API یا WP-CLI، خروجی DNS و HTTPS/TCP 443 به `updates.alookhor.ir`، `raw.githubusercontent.com` و `cdn.jsdelivr.net` را با بررسی معتبر گواهی TLS تست کنید؛ برای هر دامنه فقط HTTP status یا کد خطای cURL را اعلام کنید. در صورت مسدودبودن، دسترسی خروجی لازم را allowlist کنید. همچنین بررسی کنید چرا `https://updates.alookhor.ir/manifest.json` از بیرون 404 می‌دهد و آیا ریشهٔ FTP دقیقاً به Document Root همان زیردامنه متصل است. لطفاً TLS verification را غیرفعال نکنید.»

## ادامهٔ کار پس از تشخیص

1. از فایل‌ها و دیتابیس سایت بکاپ قابل‌بازیابی بگیرید؛ سورس افزونهٔ **فعال 3.10.390** را به‌صورت read-only از سرور یا بکاپ معتبر بازیابی و با بستهٔ GitHub مقایسه کنید. Application Password امکان خواندن PHPهای روی دیسک را به‌تنهایی نمی‌دهد؛ برای این مرحله دسترسی SFTP/SSH محدود به پوشهٔ افزونه یا یک بکاپ مطمئن لازم است (از مسیر امن، نه رمز در چت).
2. مسیر انتشار FTPS نسبت به Document Root و پاسخ عمومی HTTPS را بررسی و درست کنید. سپس تصمیم بگیرید آپدیت‌ها از کدام دامنهٔ قابل‌دسترس برای **خود وردپرس** دریافت شوند. آینهٔ GitHub فعلاً نسخهٔ 3.10.385 است و نباید به‌عنوان به‌روزرسانی 3.10.390 معرفی شود.
3. پس از یکسان‌شدن سورس، تست‌ها، بسته، کانال و نسخهٔ واقعی سایت، انتشار **نسخه‌ای جدیدتر از 3.10.390** را ابتدا روی staging و سپس با تأیید در production انجام دهید. ادغام سورس 3.10.387 روی افزونهٔ فعال 3.10.390 می‌تواند عقبگرد و حذف قابلیت ایجاد کند.
