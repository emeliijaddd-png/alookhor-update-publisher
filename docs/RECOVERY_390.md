# ALOOKHOR — مسیر بازیابی انتشار و اتصال وردپرس (۲۴ سپتامبر ۲۰۲۶؛ به‌روزرسانی وضعیت 3.10.391)

## وضعیت تأییدشده

- در بررسی تازه، `https://alookhor.ir/wp-json/alookhor-cc/v1/topbar/?fresh=20260924b` نسخهٔ فعال **3.10.391** را گزارش می‌کند؛ `readme.txt` عمومی افزونه نیز Stable tag **3.10.391** دارد. مسیر بدون اسلش آخر (`.../topbar`) در حال حاضر `rest_no_route`/HTTP 404 می‌دهد، اما همان مسیر با `/` پایانی یا `?rest_route=/alookhor-cc/v1/topbar` پاسخ معتبر دارد؛ بنابراین نبودن پاسخ از URL قدیمی به‌معنی غیرفعال‌شدن افزونه نیست. تست‌ها و gate نسخه در این PR برای استفاده از مسیر کارا به‌روز شده‌اند.
- سورس `main` این مخزن نسخهٔ **3.10.387** است. بسته/سورس کامل نسخهٔ نصب‌شدهٔ **3.10.391** در این مخزن یافت نشده است. **از سورس مخزن روی سایت نصب نکنید** تا سورس واقعی 3.10.391 بازیابی و بررسی شود.
- `https://updates.alookhor.ir/manifest.json` و ZIP نسخهٔ 3.10.387 از بیرون **HTTP 404** دارند. آخرین مانیفست ثبت‌شده در `main/public/manifest.json` نسخهٔ 3.10.385 است.
- اسکرین‌شات‌های تست cURL از `venusonlineshop.ir` به‌تنهایی اتصال خروجی سرور `alookhor.ir` را مشخص نمی‌کنند.
- در دو اجرای فقط‌خواندنی GitHub Actions، [اول](https://github.com/emeliijaddd-png/alookhor-update-publisher/actions/runs/35978744481) و [دوم پس از اعلام اصلاح نام کاربری](https://github.com/emeliijaddd-png/alookhor-update-publisher/actions/runs/35979231305)، سایت 3.10.390، کانال آپدیت HTTP 404 و آینهٔ گیت‌هاب 3.10.385 بود. `GET /wp-json/wp/v2/users/me` و `GET /wp-json/alookhor-cc/v1/status` هر دو HTTP **401** با کد وردپرس **`invalid_username`** دادند. مالک می‌گوید نام ورود `admin` است، اما مقدار Secret از این اتصال قابل مشاهده نیست؛ ممکن است Secret در محیط نادرست/با قالب نادرست ذخیره شده باشد یا login واقعی متفاوت باشد. **اعتبار Application Password و اتصال خروجی هاست وردپرس هنوز آزموده نشده است.** رمز را در چت نفرستید.
- [ممیزی FTPS فقط‌خواندنی](https://github.com/emeliijaddd-png/alookhor-update-publisher/actions/runs/35979762478) با Secretهای محیط `production` با TLS معتبر وصل شد؛ ریشهٔ قابل مشاهدهٔ حساب ۳ ورودی دارد، اما `manifest.json` و پوشهٔ `releases/` در آن پیدا نشدند (`RETR`/فهرست‌گیری: FTP 550). بررسی محدود پوشه‌های وب رایج نیز مانیفستی پیدا نکرد. این نتیجه **نشان نمی‌دهد** ریشهٔ FTP همان Document Root زیردامنه است؛ باید نگاشت FTP ↔ وب توسط هاست تأیید شود. در این ممیزی هیچ آپلود، نصب یا تغییری روی هاست انجام نشد.
- محیط GitHub **`production` اکنون Required reviewer دارد** (مالک مخزن)؛ اما محیط **`production-diagnostics` هنوز `protection_rules: []`** دارد. تلاش دوباره برای تنظیم خودکار آن با اتصال فعلی GitHub به 403 (`Resource not accessible by integration`) خورد. تا محافظت محیط تشخیص، هیچ تست احراز هویت‌شدهٔ تازه‌ای اجرا نشد و صحت Secret اصلاح‌شده هنوز نامعلوم است. مالک باید reviewer محیط دوم را هم در UI ذخیره کند یا اتصال Arena را با مجوز لازم دوباره برقرار کند. تریگر موقت FTPS از workflow نهایی حذف شده است.

## کاری که در این شاخه انجام شده

- push معمولی `main` دیگر مجوز **deploy** ندارد؛ برای انتشار، تگ نسخه و گذر از تست‌های بسته/نسخهٔ سایت لازم است.
- ساخت بسته‌ای با PHPهای جایگزین‌شده با stub یا فایل CSS/JS فراخوانی‌شده ولی مفقود، رد می‌شود؛ سورس فعلی 3.10.387 به همین علت عمداً رد می‌شود.
- قبل از تغییر مانیفست عمومی، ZIP آپلودشده با HTTPS و SHA-256 از بیرون خوانده و بررسی می‌شود؛ بعد از تغییر اتمی مانیفست نیز پاسخ HTTPS تأیید می‌شود. موفقیت FTPS به‌تنهایی کافی نیست.
- اجرای تشخیصی workflow فقط **خواندنی** است: درخواست‌های عمومی به سایت/کانال/آینهٔ گیت‌هاب و در صورت تنظیم دسترسی، فقط دو GET به `/wp-json/wp/v2/users/me` (بررسی اعتبار/مجوز) و `/wp-json/alookhor-cc/v1/status`. هیچ endpoint نصب، تغییر تنظیمات یا ثبت سفارش صدا زده نمی‌شود. خروجی هرگز متن کامل پاسخ خصوصی یا رمز را ثبت نمی‌کند.
- این تغییرات تا زمان ادغام‌شدن PR روی `main` فعال نمی‌شوند؛ **PR را پیش از تأیید شرایط استقرار/دسترسی بررسی کنید.** هیچ انتشار تولیدی با این شاخه انجام نشده است.

## حداقل دسترسی لازم برای تشخیص از خود وردپرس

1. در وردپرس، `کاربران → افزودن` یک کاربر جدا برای بررسی بسازید. **اگر** نقش `ALOOKHOR Publisher` قبلاً روی سایت فعال است، همان نقش با مجوز `update_plugins` کافی است؛ در غیر این صورت، برای شروع فقط با هماهنگی مالک یک کاربر مدیریتی **موقت** ایجاد و پس از کار لغو کنید. لازم نیست رمز ورود اصلی مدیر را به کسی بدهید.
2. در `کاربران → شناسنامهٔ همان کاربر → رمزهای کاربردی (Application Passwords)` رمز جدیدی با نام مشخص مثل `ALOOKHOR GitHub Diagnostics` بسازید.
3. در وردپرس `کاربران → همهٔ کاربران`، مقدار دقیق ستون **نام کاربری / Username** حسابی را که رمز کاربردی جدید برایش ساخته‌اید بخوانید؛ این مقدار «نام نمایشی»، «نقش»، یا رشته‌ای شامل `WP_USERNAME=` نیست. در GitHub `Settings → Environments → production-diagnostics → Environment secrets` وجود و محل Secret `WP_USERNAME` را بررسی و مقدار آن را **بدون کوتیشن، پیشوند `WP_USERNAME=` یا فاصله/سطر اضافه** با همان login دقیق ثبت کنید. اگر `WP_APP_PASSWORD` برای کاربر دیگری ساخته شده، رمز کاربردی تازهٔ همین کاربر را جایگزین کنید. Secret محیط را با Secret سطح مخزن اشتباه نگیرید. هیچ نام کاربری/رمز/اسکرین‌شات حاوی Secret را در چت نفرستید؛ `invalid_username` هنوز اعتبار خود رمز را اثبات یا رد نمی‌کند.
4. در GitHub `Settings → Environments` برای **هر دو محیط `production-diagnostics` و `production`**، خودتان را به‌عنوان `Required reviewer` انتخاب و `Save protection rules` را بزنید؛ این اتصال مجوز تغییر محیط را ندارد. تا محافظت محیط و اصلاح Secret از انجام دوبارهٔ تست‌های محتاج Secret پرهیز کنید. برای اجرای دستی workflow از طریق اتصال Arena، مجوز Actions: write لازم است؛ در غیر این صورت مالک می‌تواند در UI با approval محیط اجرای تشخیصی را آغاز کند. پس از پایان پروژه رمز کاربردی و دسترسی اضافی را لغو کنید.

## برای تشخیص واقعی محدودیت ۴۴۳ از **سرور خود آلوخور**

- پاسخ endpoint مدیریتی، درخواست سرور وردپرس به **آدرس مانیفست تنظیم‌شده** و خطای آن را نشان می‌دهد؛ درخواست‌های عمومی workflow از GitHub Runner اجرا می‌شوند و نشان‌دهندهٔ خروجی وردپرس نیستند. سورس 3.10.387 موجود در این مخزن به‌طور پیش‌فرض **`updates.alookhor.ir`** را می‌خواند و دانلود بسته را فقط از همین میزبان می‌پذیرد؛ تنظیمات واقعی نسخهٔ فعال 3.10.391 هنوز قابل بررسی نبوده است. بازشدن دسترسی GitHub/CDN به‌تنهایی 404 کانال پیش‌فرض را درست نمی‌کند.
- برای آزمون جداگانهٔ `raw.githubusercontent.com`، `cdn.jsdelivr.net` و `updates.alookhor.ir` از روی **هاست alookhor.ir**، به دسترسی WP-CLI/SSH محدود روی همان هاست یا کمک پشتیبانی میزبانی نیاز است. از پشتیبانی بخواهید با WordPress HTTP API (`wp_safe_remote_get`)، TLS certificate verification روشن و timeout کوتاه، به URL عمومی کوچک روی هر دامنه درخواست GET بزند و فقط HTTP status یا کد خطای cURL را گزارش کند. HTTP 404 با قطعی اتصال/TLS فرق دارد؛ تست روی `venusonlineshop.ir` معتبر نیست.
- اگر واقعاً ۴۴۳ برای آن دامنه‌ها از همان هاست بسته باشد، تغییر فایروال/allowlist فقط از پنل یا پشتیبانی هاست انجام می‌شود؛ رمز وردپرس یا GitHub آن را باز نمی‌کند. غیرفعال‌کردن بررسی TLS یا استفاده از پراکسی عمومی/سایت ثالث راه‌حل ایمن نیست.

**متن آمادهٔ درخواست از پشتیبانی هاست:** «لطفاً از **خود سرور میزبان `alookhor.ir`** (نه یک وب‌سایت دیگر) با WordPress HTTP API یا WP-CLI، خروجی DNS و HTTPS/TCP 443 به `updates.alookhor.ir`، `raw.githubusercontent.com` و `cdn.jsdelivr.net` را با بررسی معتبر گواهی TLS تست کنید؛ برای هر دامنه فقط HTTP status یا کد خطای cURL را اعلام کنید. در صورت مسدودبودن، دسترسی خروجی لازم را allowlist کنید. حساب FTPS انتشار فعلی با TLS وصل می‌شود ولی در ریشهٔ آن ۳ ورودی هست و `manifest.json`/`releases/` نیست (FTP 550)، و `https://updates.alookhor.ir/manifest.json` از بیرون 404 است. لطفاً Document Root واقعی زیردامنه، مسیر قابل مشاهدهٔ همان حساب FTPS و مجوز انتشار آن را با هم تطبیق دهید؛ مسیر/پاسخ بدون رمز را اعلام کنید. لطفاً TLS verification را غیرفعال نکنید و بدون بستهٔ تأییدشده چیزی منتشر نکنید.»

## ادامهٔ کار پس از تشخیص

1. از فایل‌ها و دیتابیس سایت بکاپ قابل‌بازیابی بگیرید؛ سورس افزونهٔ **فعال 3.10.391** را به‌صورت read-only از سرور یا بکاپ معتبر بازیابی و با بستهٔ GitHub مقایسه کنید. Application Password امکان خواندن PHPهای روی دیسک را به‌تنهایی نمی‌دهد؛ برای این مرحله دسترسی SFTP/SSH محدود به پوشهٔ افزونه یا یک بکاپ مطمئن لازم است (از مسیر امن، نه رمز در چت).
2. از پشتیبانی هاست بخواهید Document Root دقیق `updates.alookhor.ir` را با ریشهٔ همان حساب FTPS که Secretهای GitHub `production` استفاده می‌کنند **بدون ارسال رمز** تطبیق دهد: حساب فعلی به‌صورت امن وصل می‌شود ولی در ریشهٔ دیده‌شده نه `manifest.json` هست، نه `releases/`؛ ریشه ۳ ورودی دیگر دارد. مجوز نوشتن/مسیر مقصد صحیح را در محیط محافظت‌شده تأیید کنید، سپس فقط بستهٔ بازیابی‌شده و معتبرِ نسخهٔ نصب‌شده یا نسخه‌ای تازه‌تر را منتشر کنید، ZIP را از HTTPS بیرونی با SHA بررسی کنید و تازه بعد از آن مانیفست را فعال کنید. هرگز مانیفست نسخهٔ قدیمی 3.10.385/387 را جایگزین نسخهٔ فعال نکنید. سپس آدرس تنظیم‌شده و دسترس‌پذیری آن از **خود وردپرس** را بسنجید؛ آینهٔ GitHub فعلاً نسخهٔ 3.10.385 است.
3. پس از یکسان‌شدن سورس، تست‌ها، بسته، کانال و نسخهٔ واقعی سایت، انتشار **نسخه‌ای جدیدتر از 3.10.391** را ابتدا روی staging و سپس با تأیید در production انجام دهید. ادغام سورس 3.10.387 روی افزونهٔ فعال 3.10.391 می‌تواند عقبگرد و حذف قابلیت ایجاد کند.
